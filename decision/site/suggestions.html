SG-01 · Score every published benchmark against a fixed naive baseline, on the same rows

Problem. The site currently publishes accuracy-looking numbers without a baseline, so a reader cannot tell skill from a dumb rule. Measured Week 9: B0 favourite 86.7%, naive point-differential rule 86.7%, naive win-percentage rule 92.3%.

Evidence. decision/results/w9-out-of-sample.json baseline_winner_rules; analysis/leaderboard.json (baseline absent).

Option A — Keep as-is

Readers may mistake a baseline artefact for skill.

Cost: None · Risk: High — this is the project's core failure mode.

Option B — Always show a baseline column next to every score

Skill and luck become visually separable at a glance.

Cost: Low — one extra computed column per table. · Risk: Low.

Option C — B + a per-row verdict label ("beats baseline / ties baseline / loses")

Makes the conclusion explicit instead of inferable.

Cost: Low. · Risk: Low.

Recommended. C · Decision needed. Approve the baseline set (point differential, win percentage, always-home) as the canonical comparison group.

Status: proposed only — not implemented. Gates affected: G6 · Owner role: analysis · Official source ↗

SG-02 · Split the competition into a price-free accuracy track and a separate betting track

Problem. G5 (verified operator price), G7 (net expected value) and G8 (settled ledger) are permanently BLOCKED because no verified prices exist. Result: 0 of 8 strategies can ever be rewarded, and the leaderboard is an empty table by construction.

Evidence. analysis/validation-gates.json (G5/G7/G8 BLOCKED, eligible_strategies 0); data/flagged.json A01, A08.

Option A — Leave all gates coupled

Leaderboard stays permanently empty; no research is ever rewarded.

Cost: None · Risk: High — the reward mechanism the project asks for cannot function.

Option B — Track 1 = forecast accuracy and calibration (no prices); Track 2 = betting edge (prices required)

Track 1 becomes judgeable immediately from official results; Track 2 stays honestly blocked.

Cost: Medium — two scoring specs. · Risk: Low.

Option C — B + publish Track 1 scores for the existing 15 Week 9 lines as a pilot

First real, verifiable leaderboard entries this week.

Cost: Medium. · Risk: Medium — must be labelled a single-slate pilot, not a ranking.

Recommended. B, then C as a labelled pilot · Decision needed. Choose whether price-free accuracy is a legitimate basis for paper reward points.

Status: proposed only — not implemented. Gates affected: G6, G8 · Owner role: rules owner · Official source ↗

SG-03 · Make the site regenerate on a schedule and show its own staleness

Problem. The published dashboard is frozen at 2026-11-04 (Week 9 pre-game) while the league is in Week 10. There is no on-page indicator of how stale the numbers are, and no scheduled refresh touches them.

Evidence. data/audit-snapshot.json as_of=2026-11-04 vs official Week 9 finals on https://www.nfl.com/scores/2026/week-9 (retrieved 2026-11-14); .github/workflows/audit.yml runs a validator, uploads an artifact, and never republishes the site.

Option A — Nothing

Site silently drifts further from reality every week.

Cost: None · Risk: High.

Option B — Add a "data as of / weeks behind" banner computed from the snapshot date

Reader instantly knows the numbers are historical.

Cost: Low. · Risk: Low.

Option C — B + a scheduled job that re-runs verification and fails loudly when the snapshot lags

Drift becomes impossible to miss.

Cost: Medium — workflow change on main. · Risk: Medium — needs a maintainer to fix failures.

Recommended. C · Decision needed. Approve a publish path that updates the site (not just an artifact) and a maximum acceptable staleness.

Status: proposed only — not implemented. Gates affected: G2 · Owner role: integration owner · Official source ↗

SG-04 · Replace the depth-chart ambition with an honest availability signal

Problem. The requested 2nd/3rd/4th-string tracking cannot be built from official sources: nfl.com returns 404 for depth charts and publishes no snap counts or role data. Only position, roster status and injury designation are official.

Evidence. decision/data/availability-probe.json (AV-1..AV-6, each an observed page response on 2026-11-14).

Option A — Estimate depth order from roster/injury lists

Requires inference; violates the project's own no-inference rule and would be indistinguishable from a guess.

Cost: Low. · Risk: Critical — fabricated provenance.

Option B — Publish an official availability table only (position, designation, participation) and leave string depth blank + flagged

Truthful and useful: which positions a club has lost, not who replaces whom.

Cost: Low — data already captured this session (114 rows). · Risk: Low.

Option C — B + positional concentration metric (count of Out/Doubtful/Questionable per position group per team)

Turns availability into a comparable, source-linked number without inventing depth.

Cost: Low-medium. · Risk: Low.

Recommended. B now, C next · Decision needed. Confirm the project will accept "positions lost" instead of "2nd/3rd-string replacement" until an official depth source exists.

Status: proposed only — not implemented. Gates affected: G4 · Owner role: data owner · Official source ↗

SG-05 · Adopt a standing anti-luck evaluation protocol as a written rule

Problem. A single week produced p=0.007 against a coin flip for the benchmark, which looks like skill and is a false positive by construction when 12+ variants are registered.

Evidence. decision/results/w9-out-of-sample.json (binomial_p_vs_coinflip 0.007, winner_accuracy 0.867 tied with baseline); analysis/strategies.json (8 registered variants).

Option A — Quote raw p-values per slate

Guarantees eventual false promotion.

Cost: None · Risk: Critical.

Option B — Minimum sample floor + pre-registered family + baseline comparison, no exceptions

Most published numbers would become "insufficient evidence", which is correct.

Cost: Medium — governance. · Risk: Low.

Option C — B + publish a running "number of variants tested" counter used in the adjustment

Makes multiplicity visible to the reader.

Cost: Medium. · Risk: Low.

Recommended. C · Decision needed. Set the minimum sample floor (e.g. one full season of slates) before any skill label is allowed.

Status: proposed only — not implemented. Gates affected: G6, G7 · Owner role: rules owner · Official source ↗
